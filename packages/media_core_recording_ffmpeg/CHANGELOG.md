## Unreleased

- **Bug fix**: the verdict is now about the recording that asked for it. Three ways an unusable recording reported `success`, all of them the fixed-`filePrefix` case (a second recording of a room points at the first one's files, and `-n` means it writes nothing of its own): a journal whose bytes are unchanged from the moment before this session's process was allowed to touch it is no longer read as this session's output, and the count of them is what the `missing` reason says; a segment file older than the session is skipped rather than counted (`FfmpegSegmentJournal.fromFile`/`fromFiles` take a `notBefore`, and the backend passes its own start with two seconds of slack for coarse filesystem mtimes); and a segment listed twice — the usual shape when a dropped stream was re-opened and both attempts' journals name the same file — is counted once, so `bytes` is not the same file's size added twice.
- **Bug fix**: "opened and abandoned" is `missing`, not `suspicious`. When every segment on the list is either gone or a stub under `minimumSegmentBytes`, the recording holds nothing, and a verdict that said "some segments look wrong" while `bytes` reported 0 read as a partial success. The reason names which of the two it was.
- **Bug fix**: a recording whose journal could not be read no longer reports the *previous* attempt's verdict. `_lastCheck` was left holding the check from an earlier attempt whenever this one's journal read failed, and `stop()` returns that field — so a host asking what was kept was told about a different process's files. It is cleared on that path now, which is what "no judgement was made" is supposed to mean.

- `FfmpegDiskSpace`: the disk watermark now has an answer to give. `diskWatermarkBytes` has been enforced since the start — but only against a probe the host supplied, and Dart has no API for free space, so in practice the check sat there configured and never asked. This asks the platform the way its own users do (`df -kP` on POSIX and Android, PowerShell's `System.IO.DriveInfo` on Windows) and returns null for anything it cannot parse, because "unknown" and "full" are different answers and the second one refuses a recording. It is offered as the probe to pass (`diskSpace: FfmpegDiskSpace.probe`) rather than called by default: starting a recording should not wait on a shell the host never asked for, which is the same reason `executor` is injected.
- **Breaking** (this package is not on pub.dev yet): the keep-alive seam is the core's `BackgroundRuntime`, not a `BackgroundExecutionStarter` function. `FfmpegRecordingBackend(backgroundRuntime:)` replaces `keepAliveStarter:`; a recording acquires `recording/<prefix>` as a `BackgroundExecutionKind.recording` session, updates its own lease through the registry, and gives it up on every end exactly as before. What a host sees is the same behaviour it had — a declined or unavailable session still leaves the recording running, unprotected and logged — but the reason now arrives as a `BackgroundAcquireFailure` instead of as a null, and two backends naming the same prefix share one session (`BackgroundDuplicatePolicy.share`) instead of stacking a second service that one of them releases for both. A host that called `BackgroundExecution.acquire` directly keeps working: that API is unchanged.

- The file name follows the source. `RecordingSource` can now carry a `title`, and `FfmpegRecordArguments.filePrefixFor` prefers it over `FfmpegRecordConfig.filePrefix` and over the generated timestamp - because the address is neither stable (a signed live URL changes per session) nor safe to write into a name (its query is a credential), while the room title is the only thing a folder of files still says weeks later. `subdirectoryPerRecording` nests under that name too, the keep-alive notification line shows it, and a re-opened attempt is still `<title>_r1`. A host that wants its configured name passes a source with no title. `FfmpegLiveRecordingWatcher` fills the title in from the status probe, so watching a room names its recordings without extra wiring.

- The backend reports the recording's verdict through the core's `MediaJobReporting` slot — once per recording, from whichever terminal path closed it, so a stream that ended on its own and was then stopped by a host does not produce two lines. What is reported is the verdict the files gave (`success`, bytes, media time actually written), not the exit code, and the label is the prefix the files carry rather than the address: a signed live URL's query is a credential. With no reporter installed the call does nothing, and `stop()` returns exactly what it returned before.

- `FfmpegLiveRecordingWatcher.stop()` now reports what the session recorded. It awaited the backend's stop and then closed the session, while the recording's terminal state reaches the watcher as a stream event that is not guaranteed to have been delivered by then — so `session.recordings` was empty for a caller that stopped a watching recording and read the session immediately, which is exactly the host that wants to say what it kept. The state the backend holds is now taken directly when it is already terminal, and the event path still covers the case where it is not; either way the outcome is recorded once.

- `FfmpegLiveRecordingWatcher` watches a room instead of guessing when to record: a host-supplied `LiveRoomStatusProbe` is asked once per poll, a live room is recorded, and `onLiveStart`/`onLiveEnd` fire once per live session rather than once per poll (a flickering stream would otherwise turn twenty rooms of monitoring into noise). Polling is jittered through the core's `RetryUtils.backoff` so N rooms do not reach the platform's endpoint in the same second, a room that reports its address alongside its status is recorded at that address instead of being resolved twice, and a recording that ended within `shortRecordingAfter` is re-checked on `recheckInterval` — bounded by `maxAlmostStartRechecks`, so a room that really did close is not asked every few seconds all night. It stops polling while a recording runs: the backend's read timeout, stall watchdog and restart limit already notice a dead stream, and the watcher learns the session is over from the recording ending.

- A recording chooses its container: `FfmpegRecordConfig.container` with `FfmpegRecordContainer.mpegTs` (the default, unchanged) and `mp4Fragmented`. Both are per-segment playable and survive a kill, which is the requirement a plain MP4 (index written at the end) and Matroska (a crash mid-cluster makes the duration lie) do not meet. The segment suffix defaults to the container's, and `FfmpegRecordConfig.segmentSuffix` overrides it.
- File naming became real: `includeTimestampPrefix` now decides the generated prefix (it was documented and ignored), `subdirectoryPerRecording` gives one recording its own directory, and the sanitiser keeps the letters and digits of any script instead of folding every non-ASCII room title to `_`. A Chinese or Cyrillic anchor's name used to sanitise to nothing and fall back to a timestamp, which left a folder of files whose names said nothing about who was in them. Prefixes are capped at 64 runes.
- Every recording writes a `<prefix>.clock-v1.json` manifest (`writeManifest`): wall-clock start, container, segment length, the journals of its attempts and the source without its query string, because a signed live URL's query is a credential. `FfmpegRecordingManifest.read` reads it back and `backend.lastManifest` holds the last one.
- `backend.combineLastRecording()` and `FfmpegRecordingRemuxer` join a finished recording's segments into one file (`-f concat` + `-c copy`, MP4 `faststart`, Matroska or TS), verify the result with FFprobe and remove the list they generated. It is a separate call rather than part of `stop()` so a phone stays free to record while a merge runs, and an existing output is kept rather than rebuilt.
- `onSegmentClosed` announces each segment as the recording finishes it, driven by the journal's own growth (FFmpeg gives no callback for a rolled segment), and `segmentsClosed` counts them. The segment a recording ends on is never announced, because it was still open; that one appears only in the final `lastCheck`.

- A source that ends on its own is re-opened instead of ending the recording: jittered backoff (`FfmpegRecordConfig.restartBackoff`/`restartBackoffMax` via the core's `RetryUtils.backoff`), bounded by `restartLimit` on consecutive failures that never reached `healthyAfter`, and through `urlRefresher` when the host can mint a new address. Each attempt rebuilds its whole argument list with its own segment prefix and its own journal, because FFmpeg's `-n` refuses an existing output and the CSV list is rewritten from scratch; the final verdict reads every attempt's journal, and the reported duration is the sum of the attempts (each process counts its own timeline from zero). `restartLimit: 0` restores the old "a drop ends the recording".
- A stalled input is ended so recovery can replace it: `stallTimeout` counts checks in which neither media time nor bytes advanced — repeated statistics reports do not reset it, and FFmpeg's own `-rw_timeout` cannot see an input that keeps delivering something.
- A recording directory below `diskWatermarkBytes` is refused before the first segment and stops a re-opening, when the host supplies a `diskSpace` probe. There is no default probe: the pub.dev disk-space plugins are single-platform and unmaintained, and a wrong floor would refuse recordings that would have worked; a full disk without a probe still fails honestly, through FFmpeg's write error and the give-up report.
- `stop()` now judges the recording by its files instead of by its process. The segment journal is read back, the segments it names are sized on disk, and the first and last are opened by FFprobe, so a recording that captured nothing is reported as a failure (`FfmpegRecordingFailure`) rather than as `success: true`; a recording with a hole in it stays usable and names the hole in `FfmpegRecordingBackend.lastCheck`. The byte figure returned is the one measured from the files: with `-f segment` the statistics line's `size=` describes the child file being written, not the recording. `FfmpegRecordConfig.verifyOutput` / `verifyPlayability` switch the two layers off, and `FfmpegProbe` is injectable.
- Output paths are joined with `package:path` (`joinOutputPath`), with the separator style taken from the directory the caller was given. The three hand-rolled joins it replaced could not agree with the journal reader on where a segment lives when a Windows path was passed on a POSIX host.
- A source that restarts its timeline mid-recording no longer freezes the keep-alive notification. The update window is measured in media time (the clock FFmpeg reports on), so when a dropped live stream re-opens and reports a smaller `out_time_ms` than the last notified point, the arithmetic read "not due yet" for the rest of the session and the shade kept showing the old duration. A backwards jump now re-opens the window.
- `ffmpeg_kit_extended_flutter` is required as `^0.6.2` instead of the exact `0.6.2`. An exact pin is a single version, so an app that pulled FFmpeg in through another package could not satisfy both; `^0.6.2` still resolves to 0.6.2 today (it is the newest release), it just stops blocking the rest of the resolution.

## 0.1.0

Initial release.

- FFmpeg recording backend: captures network streams through `ffmpeg_kit_extended_flutter` and writes them out as segmented MPEG-TS.
- Wired to the kernel's recording contract: `FfmpegRecordingBackend` handles start / stop / segment rotation and failure reporting.
- Background execution: recording goes through `BackgroundExecutionStarter` to `media_core_native`'s foreground service, so it keeps going with the screen off; the session has to be taken before the process starts.
