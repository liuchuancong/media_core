## Unreleased

- `NotifyOn.startsAndResults` now means what it says. `JobNotifications` implements the reporter's new `reportStart`, and a beginning is posted quietly — the progress tone, on the results channel a user mutes to stop the chatter — because the job's own running line already says it is running wherever a service draws one, and this is the same fact told to the platforms that have no line. Under the default `results` policy a start is filtered, which is what the policy was always claimed to do.
- **Bug fix**: dismissing a line through this package now settles what `ForegroundJobs` believes about it. `isShowingLine`/`isShowingLineFor` answer about the last thing the projector tried to post, so a host that cleared a line — with `MediaCoreNotify.dismiss`, or through its own notification pipeline, now via `ForegroundJobs.lineWasRemoved(id)` — left the projector telling a lie until that feature's text happened to change. A removal the platform *refused* keeps the belief, and the repost window closes with the line: opening one is never throttled, so when the feature's own text moves the line goes up at once.

- **Bug fix**: leaving a runtime takes its lines down. `ForegroundJobs` detached its subscription and forgot its own state, but the notifications it had already posted belong to the runtime being left and the next one has no idea they exist — so installing a second runtime left a line on the shade describing work nobody holds any more, which is the same lie as a line that outlives its last job. `hide()` now awaits those clears, and `watch()` also keeps following the slot after its first attach: replacing the installed runtime was the one case the projector was written to survive a swap for and did not.
- **Bug fix**: a repost the platform refused is tried again. The line used to claim `showing`, its title and its body before calling the client, so when `showRunningLine` threw the projector believed a notification was up that nobody ever saw — and the next repaint compared its own text against that belief and skipped. Now the claim happens after the client answers, and a refusal leaves the line dirty for the end of the repost window. Both the repost and the clear catch any thrown object rather than only `Exception`: this code runs inside the runtime's change event, and an escaping `Error` cancels the subscription, which is silent job lines for every feature for the rest of the process.
- **Bug fix**: `NotifySetup.channelFor` falls back to the catch-all `media_core_jobs` channel rather than to the feature's own channel object. The whole point of the fallback is that a host trimmed that channel out of `channels`, and returning it anyway posted a line on a channel the platform never registered — a line the user cannot silence, which is the thing the fallback exists to avoid.

- **Breaking**: the running line is one per feature, not one for all jobs. `ForegroundJobs` used to project the whole runtime into a single notification (id `1`, channel `media_core_jobs`), so a download starting rewrote the recording's text and the last session of *any* feature took the line down for all of them. Each job owner now has its own line: `runningLineIdFor(owner)` for the id, `NotifySetup.channelFor(owner)` for the channel, with new `media_core_recording` and `media_core_download` channels beside the catch-all `media_core_jobs` — so a user can silence transfers and keep recordings loud. The "还有 N 个任务" count counts only that feature's other sessions, and a line whose own text did not change is not reposted when another feature moves. Consequently `LocalNotificationClient.clearRunningLine` takes the `id` it is clearing, and `ForegroundJobs.lineTitle`/`lineBody` became `titleFor(owner)`/`bodyFor(owner)` — a global-line accessor would keep the abandoned concept reachable. Opening and closing a line is still never throttled; only the moving text is.
- **Breaking**: the package no longer starts a foreground service. `LocalNotificationClient.startForeground`/`updateForeground`/`stopForeground` became `showRunningLine`/`clearRunningLine` — the same fixed-id, non-dismissible line, posted as a notification instead of through `flutter_local_notifications`' `startForegroundService`, and `NotifySetup.foregroundServiceTypes` went with it because nothing reads it any more. That path was a **second** Android foreground service (besides `media_core_native`'s job service) with its own notification for the same work, and it required every host to declare the plugin's `ForegroundService` in its manifest. The job service is now the only owner of the Android job notification, as the architecture note's decision 3 says.
- `ForegroundJobs` is a projection over the background runtime rather than a second session list. It used to keep its own `_sessions` map — which meant the jobs a host started through `ForegroundJobs.start(...)` and the leases the same jobs held through `BackgroundExecution` could disagree about what was running. Now `ForegroundJobs.watch()` follows `BackgroundRuntime.changes` and composes the line from `activeRequests` (loudest first, then by arrival, the rest counted); `runningCount`, `lineTitle` and `lineBody` are computed, not stored. `hide()` takes the line down without touching the sessions, and opening and closing the line are not throttled — only the moving text is, because a line that lingers a second after the last job ended describes work that stopped.
- **Bug fix**: nothing in the repository called `ForegroundJobs` at all, so the aggregate was correct on every question asked of it and invisible everywhere it was drawn — a recording on iOS, macOS, Windows or Linux said nothing. `MediaCoreNotify.enable()` now arms the line itself (and `disable()` takes it down, so it returns `Future<void>`); a host that wants the text without the notification can still read `lineBody` and call `hide()`. `watch()` also waits for the runtime instead of asking once: the backend a host installs at the first job is not present when `main()` enables notifications, and a projection that gave up at that moment would reproduce the same silence from the other direction.

- `MediaCoreNotify.enable()` now also turns on job outcomes. It installs `JobNotifications` into the core's `MediaJobReporting` slot, so a download that finished or a recording that stopped early reaches the tray without `media_core_download` or `media_core_recording_ffmpeg` depending on this package: 下载完成 / 下载失败 / 录制完成 / 录制中断, each with the file or prefix, the bytes, the media time actually recorded and the error when there was one. The policy is `enable`'s new `jobOutcomes` argument (`NotifyOn.results` by default, `NotifyOn.nothing` keeps the running line and drops the per-job result), and `disable()` takes back only a reporter this package installed — a reporter the host wrote itself stays where the host put it.


## 0.1.0

Initial release.

- `MediaCoreNotify`: say yes once at app start, then describe events. `post`, `dismiss`, `requestPermission`, `notificationsEnabled`, and a `NotifyOn` policy so a host can choose results only, or nothing at all. Nothing in it can fail the job it is reporting for — every platform refusal is a silent `false`.
- `NotifyTone` is what decides how insistent an event may be: a progress line is silent, only-alerts-once and non-dismissible, a result makes a noise, and a failure is loudest and stays until opened. The mapping lives in one table, so "why does this beep" has one answer.
- `ForegroundJobs`: several running jobs share one line — newest first, the rest counted — reposted at most once per second. That rule used to live inside `media_core_native`'s Android service, where nothing could see it; here it is Dart, with tests, and it behaves the same on Windows, Linux and macOS where a job line exists but no service does.
- `LocalNotificationClient` is the seam. `flutter_local_notifications` 22.x is the default implementation (`FlutterLocalNotificationsClient`) and nothing above that file touches the plugin, so a host with its own notification pipeline can pass its own client and a suite with no platform at all can assert on what would have been shown.
- The job glyphs `media_core_native` already ships (`ic_stat_media_core_record`, `_download`, `_task`) are reused as the Android small icons, so a recording never shows a download arrow.
